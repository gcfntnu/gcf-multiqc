# GCF MultiQC extensions

`gcf-multiqc` moves GCF reporting extensions out of the old MultiQC fork into an
installable plugin for **upstream MultiQC 1.35**. Version **0.1.0rc4** is a
candidate for evaluating the existing GCF report commands. It passed fresh
BFQ/workflow integration acceptance; production adoption remains pending.

The first release prioritizes compatibility with the report inputs and module
selections currently generated by `gcf-bfq` and `gcf-workflows`. Suite adoption
PRs prepare image selection and the small BFQ multi-pass correction described
below. MultiQC itself is installed unmodified; GCF code uses module entry points
and configuration hooks.

## Installation and use

Use Python 3.11 and an isolated reporting environment:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install .
.venv/bin/multiqc --version
.venv/bin/multiqc -m fastp -m fastqc_rnaseq -m custom_content /path/to/copied/logs
```

The candidate image is `gcfntnu/gcf-multiqc:1.35-gcf0.1.0-rc4`. Its recipe belongs
to [gcf-docker/gcf-multiqc](https://github.com/gcfntnu/gcf-docker/tree/multiqc/upstream-plugin-candidate/gcf-multiqc).
The published image digest is
`sha256:2c356684c03d24c11e63be5724d4f107c253eccd8be98c236952bd3df5435878`,
with plugin runtime source `4625e75315f5c89475af5ce70313642f4154ce40`,
MultiQC 1.35 and Plotly 6.0.1. This rc4 image includes the General Statistics
metadata and BCL Convert lane-count/label corrections below. The previous rc1
and rc2/rc3 artifacts retain their original digests for historical comparison.
The image provides `multiqc` on PATH and `/opt/images/logo_ntnu.png`, and has no
forced entry point. It is suitable for explicit Docker commands and later
evaluation with the suite's existing Apptainer wrapper. Image publication does
not switch the suite to it.

```bash
docker run --rm --network none --user "$(id -u):$(id -g)" \
  -v "$PWD/copied-logs:/inputs:ro" -v "$PWD/reports:/output" \
  gcfntnu/gcf-multiqc:1.35-gcf0.1.0-rc4 \
  multiqc --no-version-check --no-ai --no-megaqc-upload \
  -m fastp -m fastqc_rnaseq -m custom_content -o /output /inputs
```

Create the `reports` directory first. Existing GCF YAML files can be supplied
with `-c`. Input logs are read only; outputs belong in a separate directory.
Do not install the reporting package into BFQ's orchestration environment:
BFQ owns a `multiqc` container wrapper with the same command name.

## Compatibility contract

| Existing selection / behavior | Candidate implementation |
| --- | --- |
| `fastqc_rnaseq` | Upstream FastQC parsing and plots, separate paired-mate identities, historical section IDs, no FastQC General Statistics columns. |
| `fastp` | Upstream parser/plots; retain input read count and GCF survival percentage column identity. |
| `star` | Upstream parser; preserve GCF column keys with explicit aligned-read and splice-event meanings. |
| `cellranger` | Historical GCF mkfastq `qc_summary.json` adapter. This selector means mkfastq in compatibility mode. |
| `cellranger_count` | Historical count `*.metrics_summary.csv` adapter, with normalized numeric exports. |
| `starsolo` | GCF staged `*_Summary.csv` summaries. Plain `Solo.out/Gene/Summary.csv` is not automatically treated as a sample. |
| `parse` | Both historical aggregate-summary CSV orientations; one summary per input library plus the separately named aggregate. |
| `qiime2` | Exported DADA2 metadata, taxonomy CSVs and DEICODE ordination with appended sample metadata. |
| `unitas` | Annotation composition, sequence lengths and miRNA detection. |
| `bracken` | Separate Bracken report identity using upstream Kraken's parser. Filename-based discovery keeps estimated counts separate from Kraken observations. |
| Custom content | Literal sample IDs preserved, including leading zeros and filename-like identifiers. Existing PCA/UMAP data are adapted in memory to upstream plotting. |
| BCL Convert | Upstream parser/plots with additive sample/lane chunks for multiple index rows; weighted quality and distinct index sequences are retained. |
| Other standard modules | Upstream implementations, including bcl2fastq and InterOp. |

Custom General Statistics columns with GCF's plain-text `format: '{}'` preserve
string values such as `0007`, `NA` and `NaN` in the rendered HTML and TSV/JSON
exports. Text is escaped for HTML. Actual numeric values and columns with numeric
formats retain upstream numeric parsing and formatting; absent values remain
absent. This correction is tracked in [issue #3](https://github.com/gcfntnu/gcf-multiqc/issues/3).

Acceptance prioritizes active workflow families, Parse, Cell Ranger count and
sequencing reports. QIIME2 and legacy mkfastq are deprecated for suite migration;
their existing adapters remain available but are not adoption gates. STARsolo
has lower testing priority because BFQ no longer runs it by default.

Bracken accepts Kraken-format `*.bracken`, `*.bracken_kreport`, and
`*.bracken.kreport` files. The abundance-table TSV (`*.bracken.out`) is a different
format. The existing workflow ignores original Bracken kreport files and stages
the intended reports with `.bracken` names; this remains supported. Kraken
reports without unclassified reads remain Kraken reports. Selecting only
`kraken` retains upstream's ability to parse either report format.

`gcf_compatibility: true` is the default. It deterministically substitutes GCF
adapters for `bclconvert`, `cellranger`, `fastp`, `star`, and `custom_content` through supported
configuration hooks, and restores the historical filename-cleaning suffixes.
It does not register competing entry points with those upstream names.

To use the native upstream meanings, set:

```yaml
gcf_compatibility: false
```

The additional GCF modules remain available. Explicit selections `gcf_fastp`,
`gcf_star`, and `gcf_cellranger_mkfastq` allow individual adapters alongside
native modules. The mkfastq alias uses a distinct report anchor and export name;
native `cellranger` plus this alias is tested. Select the intended count parser
instead of reporting the same count run through native Cell Ranger and the GCF
CSV adapter simultaneously. Explicit aliases are omitted from default
all-module scans unless selected in `module_order`.

## Deliberate corrections

Compatibility does not preserve known numerical defects:

- FastQC plots retain separate R1/R2 identities. The fork's shared filename
  cleaning merged mates and kept whichever archive was parsed last. The scoped
  adapter preserves both mates without changing other modules' metadata joins
  or adding FastQC General Statistics columns. See
  [issue #6](https://github.com/gcfntnu/gcf-multiqc/issues/6).
- Unitas miRNA fractions use each sample's own total. A zero total is unavailable,
  not a fabricated percentage.
- STAR's splice counts describe **events**, not distinct reads. The event/read
  ratio can exceed 100%; zero input reads yield unavailable ratios. The plot
  shows event counts instead of an invalid spliced/unspliced read partition.
- STAR's `total_mapped` and `total_mapped_percent` keys now describe uniquely
  mapped plus multimapped reads, excluding reads mapped to too many loci. The
  visible labels are **Aligned reads** and **% Aligned**, with that definition
  in their descriptions. The legacy fork included the too-many-loci category.
- Missing QIIME ordination metadata raises a bounded error instead of hanging.
- Duplicate identities in the GCF parsers raise an error instead of silently
  overwriting another sample. Malformed numeric inputs fail explicitly.
- Cell Ranger count exports contain numbers, with percentages in percentage
  points. Parse, STARsolo and mkfastq fractions retain their historical scale.
- PCA/UMAP tooltips identify samples, preserve group membership and colors,
  and use the selected component axes. Existing coordinates are not recomputed.
- Taxonomy plots calculate total fragments from root-clade plus unclassified
  counts. The legacy direct-assignment sum can undercount redistributed Bracken
  reports and reduce the Other category. Taxon counts remain tied to the source;
  percentages use the corrected total. Top-five lists can choose a different
  taxon when scores tie, without changing those taxa's source counts.
- BCL Convert sample/lane chunks sum all index rows rather than retaining only
  the last row. Counts-per-lane plots agree with sample totals, modern and older
  quality metrics retain their weights, and index labels list all distinct
  sequences. Colliding lane names across sequencing runs include the run ID.
  See [issue #4](https://github.com/gcfntnu/gcf-multiqc/issues/4) and
  [issue #5](https://github.com/gcfntnu/gcf-multiqc/issues/5).

Reports use upstream's modern presentation. Pixel-for-pixel equivalence with
the fork's old template is not a target. The unused legacy template and `fastv`
module have not been ported; they are not selected by the seven audited current
workflow profiles.

## Development and verification

```bash
python3.11 -m venv .dev/venv
.dev/venv/bin/python -m pip install -e '.[dev]'
.dev/venv/bin/ruff check src tests
.dev/venv/bin/ruff format --check src tests
.dev/venv/bin/python -m pytest -q
.dev/venv/bin/python -m build
```

Tests include real installed-MultiQC report rendering with `--strict`, numeric
export assertions, malformed/zero/duplicate inputs, the seven unchanged public
workflow templates, custom-content identity, and native sequencing-report
parsers. Suite command tests cover a relative full-path `--filename`, separate
log/figure inputs, BFQ sequencing tables and output paths containing spaces.
For planned separate conversion passes, BFQ must select `custom_content` only
once in `module_order`; repeating it creates duplicate report sections. The
correction is tracked in
[gcf-bfq #173](https://github.com/gcfntnu/gcf-bfq/issues/173).
Network and SMTP connections are blocked in report test subprocesses.
Fixtures are synthetic or public software configuration; they contain no
customer data. Private acceptance inputs must stay under ignored `.dev/` paths
and must never be included in an image build context or commit.

See [the migration checkpoint](docs/migration-checkpoint.md) for source
provenance, validation boundaries and the next adoption steps. Review work is
coordinated in [gcf-multiqc #2](https://github.com/gcfntnu/gcf-multiqc/issues/2),
[gcf-workflows #221](https://github.com/gcfntnu/gcf-workflows/issues/221),
[gcf-bfq #173](https://github.com/gcfntnu/gcf-bfq/issues/173) and
[gcf-docker #2](https://github.com/gcfntnu/gcf-docker/issues/2).
These PRs can be prepared now; merging, deployment and real-data acceptance are
separate decisions. A future MultiQC upgrade should update the exact dependency
pin and rerun these tests before publishing another candidate.
